> **基线**：Foresight Alpha `main` (`05714281acb2f86bbf168c581aca54ec82f7974d`)  
> **推荐结论**：**方案 B（模块级优化：保留 PIT DuckDB 与验证门禁骨架，选择性引入 PyAlex、BERTopic 与 PreScience/Qlib 规范）**

## 一、五大核心架构问题研判

### 问题 1：技术机会如何被自动发现？
- **能否脱离人工清单**：可以，但不能直接用无监督聚类结果替代最终投资池，必须拆分为**“候选发现池（Data-Driven Candidates）→ 稳定性过滤 → 研究跟踪池”**两级机制。
- **技术路径（基于 PyAlex + BERTopic）**：
  1. 利用 `PyAlex` 拉取开放论文标题与 `invert_abstract` 摘要，按年度窗口切分；
  2. 参考 `BERTopic`（`partial_fit` + `topics_over_time` + `merge_topics`），使用预训练语义嵌入替代纯 TF-IDF 词袋聚类；
- **误报、重复主题与漂移控制**：
  1. **防误报**：要求候选主题同时满足跨机构分散度（Shannon 熵阈值）与连续 $\ge 2$ 个季度/年度窗口持续出现（过滤单次会议专题噪声）；
  2. **防重复**：利用嵌入相似度 + `BERTopic.merge_topics` 与人工同义词映射表合并近义主题，分配永久 `topic_id`；
  3. **防历史未来主题泄露**：回测截面 $T_0$ **严禁使用包含 $T_0$ 之后文献拟合出的主题词表**；只能用 $\le T_0$ 语料增量训练的主题发现快照。

### 问题 2：技术成长到底预测什么？
必须物理剥离五类完全不同的指标（不可混用标签）：
1. **科研活跃度增长**：公开论文数、按年截断引用数增速（`Task A`，V1.2 优先验证，数据立即可得）；
2. **技术成熟度**：开源生态活跃度、临床/专利/标准阶段转换（需历史归档，GitHub 当前 Star 不可回溯历史）；
3. **产业商业化增长**：代表企业相关业务营收倍数、出货量（`Task B`，需年报公告日 PIT 快照）；
4. **企业经营业绩增长**：毛利率、ROIC、现金流健康度；
5. **投资资产收益**：指定可交易证券复权全收益（`Task C`，需行情与分红数据）。
- **V1.2 优先验证目标（参考 PreScience）**：先验证 **Task A**（未来 1y/3y/5y 领域论文增量与高引增速的对数误差 `log_mae` 与排序 `spearman`），并要求显著击败简单基准（`Poisson` / `Ridge` / 动量外推）。

### 问题 3：怎样真正实现 Point-in-Time（PIT）？
参考 Qlib `DataHandlerLP`（训练/推理处理器分离）、`RollingGen(label_leak_n)` 与 PreScience 轨迹截断，V1.2 历史数据快照最小表结构必须包含 9 个强制字段：
1. `record_id`（原始数据唯一标识）
2. `raw_payload` + `raw_hash`（原始内容与规范化 SHA-256）
3. `ingested_at`（采集时间）
4. `published_at` + `evidence_url`（实际公开时间及来源凭证）
5. `data_version`（数据快照版本）
6. `feature_version`（特征计算逻辑版本）
7. `label_period_end`（标签观察期终点）
8. `label_available_at`（标签首次可获取时间）
9. `train_cutoff_date`（模型训练截断日）
- **铁律**：GitHub Search API 当前 Star、未拆分 `counts_by_year` 的 OpenAlex 总引用、`MANUAL_REFERENCE` 人工表**显式标记为 `NOT_ELIGIBLE_FOR_STRICT_BACKTEST`**。

### 问题 4：现有模型应该保留还是替换？
| 现有模型 | 代码位置 | 真实数据现状 | 评估结论 |
| :--- | :--- | :--- | :--- |
| **LightGBM** (`LightGBMGrowthForecaster`) | `src/diffusion/lgbm_forecaster.py` | 缺真实 `VERIFIED` 多赛道面板 | **保留骨架**（治理极佳），但先增加 Ridge/Poisson 简单基准对照（PreScience 范式），用分位数或保形区间替代 `0.12 * horizon` 启发式区间。 |
| **GMM-Regime** (`MacroHMMRegimeModel`) | `src/macro/hmm_regime.py` | 仅 28 条 `MANUAL_REFERENCE` | **暂保留或简化为规则宏观过滤**，待补充官方宏观初值后再评估是否改用 `hmmlearn`，不优先投入。 |
| **Cox 生存模型** (`CompanySurvivalEngine`) | `src/risk_survival/survival_cox.py` | 23 条手写队列，且上游喂入假字典 | **保留算法，修复数据供给**：阶段 2 接入真实财报公告队列；立即清除 `24.0`/`1.0` 静默默认填充。 |
| **S 曲线** (`SCurveDiffusionModel`) | `src/diffusion/s_curve.py` | 仅拟合 `papers_count` | **保留作研究辅助指标**（衡量文献阶段位置），但**绝不作为投资倍数或商业化预测**。 |
| **Monte Carlo** (`AsymmetricPayoffEngine`) | `src/payoff_engine/monte_carlo.py` | 估值倍数写死 `25.0` | **保留场景模拟与 `SimulationType` 隔离**，待 Task B/C 真实数据就位后再校准分布参数。 |

### 问题 5：怎样实现自动研究与持续进化？
参考 `microsoft/RD-Agent` (`proposal.py`、`evolving_agent.py`)，建立四角色分离的受控循环：
`研究假设 (Research Agent) → 数据快照与特征构建 (Data/Feature Layer) → 代码实验执行 (Coding Agent) → 样本外与 PIT 独立验证 (Validation Service + Audit Agent) → 保留或拒绝`
- **职责边界铁律**：
  1. 研究/开发 Agent 生成的因子与解释**绝不直接作为真实经济证据**；
  2. 所有实验必须记录：`data_version`、`git_commit_sha`、`model_params`、`random_seed`、样本外指标（`log_mae` / `spearman` / `c_index`）及失败原因（`Trace` 不可变台账）。

## 二、三种技术方案深度对比

### 方案 A：最小改造（Pure Patch）
- 仅修补现有 `openalex.py`（加 `counts_by_year`）、`opportunity_pool.py` 的 `is_verified` 传递 bug，继续沿用硬编码 6 主题和现有手工框架，不引入 `PyAlex` 与 `BERTopic`。

### 方案 B：模块级优化（**推荐方案**）
- **保留**：`src/core/`（DuckDB + Pydantic 契约）、`src/decision_engine/model_validator.py`（OOS 反作弊门禁）、`src/backtest/`（PIT 回测骨架）与双轨排序设计；
- **升级/引入**：
  1. 用 **`PyAlex`** 重构 `src/ingestion/openalex.py`，配合原始快照存证与 `counts_by_year` 截断；
  2. 借鉴 **`PreScience`** 重构 Task A 标签定义、对数指标与简单基准对照；
  3. 借鉴 **`Qlib`** `DataHandlerLP` / `RollingGen(label_leak_n)` 改进内部训练数据切分（不引入整套 Qlib）；
  4. 第二阶段引入 **`BERTopic`**（`partial_fit` + `merge_topics`）扩展候选主题发现；
  5. 阶段 2/3 对接真实公开财报与行情，逐步替换 `enterprise.py` / `asset_mapping.py`。

### 方案 C：较大规模架构调整（Framework Rewrite）
- 以 Qlib 作为底层数据与回测引擎重写数据仓、训练、回测层，并直接集成 RD-Agent 作为顶层调度。
- **风险与代价**：Qlib 面向日频/高频证券矩阵（强绑定二进制 dump 格式与交易撮合回测），强行承载跨年论文/文本/企业公告混合研究需要大量魔改；且重写会破坏 V1.1 刚刚验证完备的 `model_validator.py` 与 109 个 PIT 防护测试。

### 三方案八维评估表（工作量基于模块拆分估算区间）

| 评估维度 | 方案 A（最小改造） | 方案 B（模块级优化 · 推荐） | 方案 C（大规模重写） |
| :--- | :--- | :--- | :--- |
| **研发复杂度** | 低 | **中等（可控）** | 极高（跨框架适配复杂） |
| **开发工作量估算** | 约 1–2 周（仅修补 P0 采集与 Bug） | **约 4–6 周（分 5 阶段小步交付，每阶段 1 周左右）** | 约 10–16+ 周（重写数据仓+适配器+重建测试） |
| **现有代码复用率** | ~90% | **~75%（保留全部门禁与 DuckDB 底座）** | <35%（大量逻辑需重写） |
| **数据建设难度** | 高（手写采样易出错） | **中（PyAlex + 快照自动化）** | 极高（需转为 Qlib 二进制格式） |
| **算法能力提升** | 极低（仍无法发现新主题） | **高（数据驱动发现 + 简单基准校准 + PIT 严密）** | 高（但受限于证券框架假设） |
| **真实预测验证可行性** | 低（样本过少，缺跨期自动化） | **高（天然契合多源异构与多年期验证）** | 中（交易撮合回测反而不适配长周期技术研究） |
| **后期维护成本** | 中（手写采集与主题清单僵化） | **低（依赖清晰、可独立替换）** | 高（升级 Qlib/RD-Agent 耦合风险大） |
| **是否适合单人 + Coding Agent** | 适合，但天花板低 | **最适合（模块化、测试边界清晰）** | 不适合（上下文过重，易失控） |

## 三、推荐决策、不选原因与翻转条件

- **推荐选择**：**方案 B（模块级优化）**。
- **不选方案 A 的原因**：无法解决主题写死（6 个预设赛道）与手写采集脆弱问题，研究系统缺乏自主发现能力。
- **不选方案 C 的原因**：Qlib 的交易级矩阵数据模型与 Foresight Alpha 的“文献+文本+公告+多年期演化”异构长周期研究错配，重写成本远大于收益且破坏现有 109 项可信度测试资产。
- **方案翻转条件**：
  - 若未来项目转向**纯粹的 A 股/美股日频量价多因子交易策略**（不再做技术文献与产业生命周期研究），则应翻转为**方案 C（直接采用 Qlib + RD-Agent）**；
  - 若资源极度受限、仅需在 1 周内针对单一赛道（如固态电池）跑通人工抽样演示，则暂时退回**方案 A**。
